# 크레팬스 정식 출시 검수 시나리오

작성 기준일: 2026-10-08. 대상은 자체 인증과 `/api/v1`에 연결된 `/service`이다. `/preview`는 디자인 검수에만 사용하며 보안·거래 합격 증거로 사용하지 않는다. 피드는 전체 최신순을 유지하고 개인화·Redis 고도화는 이 검수 범위에 넣지 않는다.

이 목록은 검수 계획이며 아래 시나리오의 실행 상태는 모두 **미실행**이다. 기존 로컬 테스트 결과와 이번 출시 검수 결과를 구분한다. 여러 계정으로 화면을 통과하는 것 외에 직접 API 요청, 실제 공급사 테스트, 금액 대사, 배포·복구 검수가 필요하다. 금전 손실과 권한 누출의 잔여 위험을 0이라고 보장하지 않으며, 출시 판정은 아래 필수 조건과 증거를 충족했을 때만 한다.

## 검수 환경과 기록

- 계정마다 별도 브라우저 프로필을 사용한다. 시크릿 창 여러 개는 세션을 공유할 수 있으므로 독립 계정 환경으로 간주하지 않는다. 같은 계정의 다중 탭 검수는 별도로 수행한다.
- 우선 실제 배포 구성과 같은 격리 검수 서버, 검수 DB, 테스트 SMTP/PASS/PG/은행을 사용한다. 기존 운영 DB나 실 사용자의 거래를 수정하지 않는다. 테스트 키와 라이브 키·거래 ID를 섞지 않는다.
- 시각 조작은 격리 DB/테스트 시계만 사용한다. 운영 서버 시간을 바꾸지 않는다. 월말·윤년·갱신일은 실제 날짜 사례로 재현한다.
- 실행 구분: **화면**은 직접 따라 하는 검수, **API**는 개발자 도구/HTTP·통합 검수, **장애**는 지연·중단·동시성 주입, **공급사**는 공식 테스트 환경, **운영**은 배포·대사·복구 검수다. 화면만으로 API·장애·공급사 항목을 통과 처리하지 않는다.
- 각 ID에 환경·프론트/백엔드 커밋·사용 계정·전제 데이터·시각·예상/실제 결과·화면/API 증거·주문/구독/정산 ID·PG/은행 조회 결과·담당자·판정을 기록한다. 상태는 미실행/통과/실패/차단/승인된 제외다. 비밀키·빌링키·쿠키·계좌번호·인증 코드는 증거 파일에서 제거한다.
- 기능이 없거나 외부 키가 없으면 **차단**이다. 테스트 대역으로 통과한 항목은 대역 결과로만 기록한다. 출시 범위에서 제외하려면 관련 UI뿐 아니라 API·worker 동작도 비활성화하고 사용자 안내를 맞춘다.

## 계정과 게시물 준비

| 계정 | 역할과 초기 상태 |
| --- | --- |
| G | 비로그인 |
| C1 | 크리에이터 하늘, 멤버십 P1 10,000원/P2 20,000원 운영 |
| C2 | 다른 크리에이터, 별도 멤버십 Q1 운영 |
| F0 | 미구독 팬, 유효한 결제수단 없음 |
| F1 | C1 P1 유효 구독, 카드 A/B 등록 |
| F2 | C1 P2 유효 구독. P1 전용 글은 권한 없음 |
| F3 | C2 Q1만 구독 |
| F4 | C1 P1 자동 갱신 해지, 결제 기간은 남음 |
| F5 | C1 P1 만료 또는 환불 완료 |
| F6 | 결제 실패·불확실 결과·동시 요청 전용 팬 |
| U1 | 회원가입·미인증·비성인 상태 검수용. 공급사 허용 테스트 신원 사용 |
| A1 | 활성 운영 관리자 |
| A2 | 권한이 제한된 운영자 또는 비활성 관리자 |

계정·상태를 준비하는 개발용 입력값으로 권한을 임의 생성한 검수와, 공식 공급사에서 가입·결제를 마친 계정 검수를 구분한다. PASS 신원 중복 계정 정책은 먼저 결정한다. 검수용 가격도 공급사 최소 금액과 계약 범위 안에서 사용한다.

C1에 공개 글 PUB, P1 전용 글 PAID1, P2 전용 글 PAID2, 임시저장 DRAFT, 예약 SCHEDULED, 삭제 DELETED, 성인 제한 ADULT를 만든다. C2에는 Q1 전용 글 OTHER를 만든다. 각 글의 본문·댓글·답글에 서로 다른 식별 문구를 넣고 이미지·동영상·미디어 10개 게시물을 준비한다. 진짜 재생 가능한 MP4/WebM을 사용한다.

PAID1 기준: C1/F1/F4는 허용, G/F0/F2/F3/F5는 차단한다. 성인 제한은 구독 외에 성인 인증도 요구한다. 잠긴 글의 제목·작성자·집계는 현재 공개 안내 정보다. 제목 자체까지 숨길 정책이면 별도 결정한다. 기존 레벨 방식으로 이관된 글은 신규 정확한 상품 방식과 분리 검수한다.

## 가입과 세션

| ID | 실행 | 시나리오와 합격 조건 |
| --- | --- | --- |
| A01 | 화면·공급사 | U1이 이메일 인증→PASS→약관 동의→가입→로그인한다. 각 서버 증명이 확인되기 전에는 가입되지 않고 가입 후 새 세션이 발급된다. |
| A02 | 화면·API | 인증번호 오입력·10분 만료·재사용·다른 이메일의 증명을 시도한다. 가입/이메일 변경 권한이 생기지 않는다. |
| A03 | 화면·API | 인증 요청 후 이탈→새 브라우저에서 같은 이메일 재요청한다. 서버 기준 3분 쿨다운, 제한 후 정상 재요청, 제한 우회/코드 유출 없음. |
| A04 | API·공급사 | PASS 취소·시간 초과·서명 위조·다른 attempt/state/목적·다른 사용자·중복 콜백을 시도한다. 가짜 인증과 중복 가입/출금 인증을 거부한다. |
| A05 | 화면·API | 필수값 누락·비밀번호 불일치·중복 이메일·약관 미동의와 verified=true 변조를 시도한다. UI와 서버 모두 거부한다. |
| A06 | 화면·API | 이메일/비밀번호 조합과 반복 로그인·코드 추측을 시험한다. 유효한 인증만 허용하고 정한 속도 제한을 적용한다. 타인의 계정 존재·비밀값을 불필요하게 노출하지 않는다. |
| A07 | 화면·API | access 만료→refresh→여러 탭 동시 갱신→이전 refresh 재사용을 시험한다. 권한 상승/회전 토큰 재사용이 없고 정상 다중 탭이 불필요하게 로그아웃되지 않는다. |
| A08 | 화면·API | 로그아웃·비밀번호 변경/재설정·탈퇴 후 이전 access/refresh 쿠키로 요청한다. 정책상 철회할 세션은 무효, 이전 본문·댓글이 다른 계정 화면에 남지 않는다. |
| A09 | API·운영 | HTTPS에서 쿠키 HttpOnly/Secure/SameSite 설정과 외부 Origin·Origin 없는 인증 쓰기 요청을 시험한다. CSRF로 결제·설정·출금이 실행되지 않는다. |
| A10 | 화면·API | 탈퇴 시 갱신 구독/출금 처리 중 상태, 탈퇴 재가입, 기존 거래 열람·보존을 시험한다. 결제가 몰래 계속되지 않고 보존/삭제 정책과 맞는다. |

세션 보호와 권한 검사는 [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)와 [권한 검사](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)를 기준으로 한다.

빌링 등록·승인은 [Toss v2 연동](https://docs.tosspayments.com/guides/v2/billing/integration)과 [코어 API](https://docs.tosspayments.com/reference)를 따른다. 공식 문서의 자동결제 승인 타임아웃은 최소 60초이며 현재 코드는 65초다. 등록 성공이 잔액/한도에 따른 다음 청구 성공을 보장하지 않고, 테스트 카드 검증은 라이브와 다르다. [Toss FAQ](https://docs.tosspayments.com/resources/faq)

같은 거래의 재시도는 동일한 멱등 식별자를 유지한다. 확정 실패 뒤 새 청구 시도는 별도 거래 상태로 구분하며, 공급사의 멱등 보장만 믿고 DB 중복 제약/거래 대사를 생략하지 않는다. [Toss 멱등성 설명](https://docs.tosspayments.com/blog/what-is-idempotency)

## 금전 시나리오의 공통 합격 조건

1. 같은 거래가 반복/동시 실행되어도 고객 청구·환불·송금은 1회다. 주문·구독·원장 반영도 1회이며 외부 결과와 대사된다.
2. 승인 없는 유료 권한, 권한 없는 파일, 원인 불명 차액, 가용액보다 큰 출금 예약이 없다.
3. 결과 불확실은 실패/성공으로 추정하지 않는다. 같은 거래를 조회해 복구하고 장기 미확인은 담당자에게 전달한다.
4. 해지·만료·환불과 worker의 경합이 계약 밖 청구/권한 부활을 만들지 않는다.
5. 마스킹 화면만 보고 합격하지 않는다. PG 거래 조회·DB 주문/구독/원장·정산/은행 결과까지 연결해서 확인한다.

## 출시 판정

- 위 시나리오는 출시 범위에 포함되는 한 모두 필수다. 권한 누출·중복 청구/환불/송금·손실·중대 취약점은 1건이라도 미해결이면 출시를 중단한다. 비금전 화면 결함의 예외는 영향·회피방법·담당자·기한을 승인 기록으로 남긴다.
- 자동 단위·DB/HTTP 통합·핵심 브라우저 E2E를 동일 릴리스에서 실행하고, 역할/상품/소유권 권한표와 동시성/장애 회귀 검사를 CI에 포함한다. 자동 검사는 전용 보안 점검을 대체하지 않는다. [OWASP 권한 회귀 자동화](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Testing_Automation_Cheat_Sheet.html)
- 실제 공급사 테스트 결과, 라이브 계약/배포 확인, 금액 대사, 백업 복구, 경보·롤백·고객지원이 있어야 한다. 테스트 환경 통과만으로 무제한 정식 운영을 승인하지 않는다.
- 현재 알려진 출시 차단/확인 과제: PASS/은행 공식 bridge와 실제 연동, SMTP/Toss 실제 연동 검수, 운영 런타임 전환, S3 공개 정책/이관, 의존성 중대 취약점 검토, 97개 전체 시나리오 자동화·원격 CI 실행, 복구/부하/경보, 환불·경합·지급 정책. 이전 로컬 269/19/17 통과는 이 전체 출시 목록의 완료가 아니다.
- 초기 운영은 승인된 회원/거래 한도와 모니터링으로 시작하며, 이상 청구/누출 발견 시 신규 결제·갱신·출금을 각각 중단할 담당자와 절차를 둔다. 코드 구현 여부와 공급사 계약 충족 여부를 별도로 확인한다.
